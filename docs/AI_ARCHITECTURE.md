# AI architecture — local only

**Hard constraints:** runtime AI is on-device; no paid cloud AI API on any runtime path; private content is never silently sent to a remote provider; no fake AI.

```text
AIService ─► AIProvider ─► LocalInferenceProvider (native runtime)   [today: no provider bundled ⇒ availability() = unavailable/no_runtime]
```

Implemented (`packages/ai`, 7 tests): `AIProvider` contract (streaming, `AbortSignal` cancellation, `unload`), `AIService.availability()/ask()/cancel()`, `selectModel()` (memory ≤ 60% of RAM, storage ×1.5 headroom, low-power/battery pause),
`buildGroundedPrompt()` with trust labels (`verified | student_generated | ai_generated | unverified`) and citation rules, `AIUnavailableError(reason)`. The Profile screen shows the real availability detail.

## Model management (to build)

Catalogue (`MODEL_CATALOGUE`, empty until models are vetted) → download manager (resumable, checksum, storage check) → load/unload lifecycle tied to screen focus → telemetry limited to non-content metrics.

## Grounding

Assistant answers must be grounded in Learning Loop content where possible; sources carry trust labels; uncertain output must be labelled (no guarantee claims). Student/AI-generated material is never presented as verified.

## Content generation (pipeline, not runtime)

Official content may be generated by controlled admin/dev automation; metadata recorded in provenance (`model_identifier`, `model_version`, `prompt_version`, `generated_at`, sources, validation/review status). The mobile app does not depend on it.
